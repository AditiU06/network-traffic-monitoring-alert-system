# Network Traffic Monitoring and Alert System (NTMS)
## Complete Technical Architecture, Engine Specifications, Algorithms & Viva Defense Guide

---

## 1. Executive Project Summary

The **Network Traffic Monitoring and Alert System (NTMS)** is an enterprise-grade, modular network security and performance analytics platform. It is engineered to ingest high-volume, multi-format network telemetry logs generated by **Zeek (Bro) Network Security Monitor**, execute concurrent multi-process log parsing, detect network intrusions and anomalies using a rule-based engine, persist events and alerts in a normalized transactional relational database, and expose real-time threat intelligence through an interactive administrative dashboard and REST API.

### Core Value Proposition
- **High Concurrency & Throughput:** Pure Python multi-core worker pool (`ProcessPoolExecutor`) delivering parallel processing speedup over large log volumes while bypassing Python's Global Interpreter Lock (GIL).
- **Comprehensive Threat Detection:** 100% test coverage of **38 Zeek Excel Transport & Network Alert Rules** plus 7 supplementary stateful heuristics (Port Scans, Address Sweeps, SYN Floods, Christmas Tree packets, Fragment Inconsistencies, Blacklisted IPs).
- **Enterprise-Grade Persistence:** SQLite 3 in **Third Normal Form (3NF)** with **Write-Ahead Logging (WAL)**, foreign key constraints, keyset cursor pagination, and retry backoff.
- **Role-Based Security:** Granular token-based authentication and authorization across System Administrators, Security Analysts, and NetOps Administrators.

## 2. End-to-End System Pipeline & Data Lifecycle

The platform operates on a sequential, decoupled 5-stage pipeline:

$$\text{Zeek Logs} \xrightarrow{\quad} \mathbf{E1} \xrightarrow{\quad} \mathbf{E3} \xrightarrow{\quad} \mathbf{E2} \xrightarrow{\quad} \mathbf{E3} \xrightarrow{\quad} \mathbf{E4 \text{ Dashboard}}$$

```
┌──────────────────┐     ┌────────────────────────────────────────────────────────┐
│  Raw Zeek Logs   │ ==> │ E1: Concurrent Log Processing Engine                   │
│ (18 log formats) │     │ (Hex separator decode, chunking, ProcessPoolExecutor)  │
└──────────────────┘     └──────────────────────────┬─────────────────────────────┘
                                                    │ Parsed & Validated Events
                                                    ▼
                         ┌────────────────────────────────────────────────────────┐
                         │ E3: Ingestion Persistence Layer                        │
                         │ (Batch SQLite insert, 3NF schema, WAL mode, audit log) │
                         └──────────────────────────┬─────────────────────────────┘
                                                    │ Keyset-Paginated Event Batches
                                                    ▼
                         ┌────────────────────────────────────────────────────────┐

                                                    ▼
```

## 3. Engine-by-Engine Architectural Breakdown

### Engine 1 (E1): Concurrent Log Processing Engine
* **Location:** `E1_Concurrent_Log_Processing/` (`e1_processor.py`, `models.py`)
* **Core Role:** Ingests raw ASCII Zeek logs, decodes headers dynamically, normalizes data types, concurrently parses records across CPU cores, and measures genuine performance telemetry.
* **Key Features:**
  1. **Dynamic Header & Separator Parsing:** Decodes hex escape sequences (`#separator \x09`, `\x20`, escapes), mapping field headers dynamically without hardcoded column indices.
  2. **18 Supported Zeek Log Types:** Full coverage for `conn`, `weird`, `notice`, `tunnel`, `dns`, `http`, `ssl`, `x509`, `files`, `ssh`, `ftp`, `smtp`, `dhcp`, `arp`, `dpd`, `capture_loss`, `known_hosts`, and `known_services`.
  3. **Strict Data Integrity:**
     - Preserves fractional microsecond timestamp precision (`1526763439.123456`) without fabrication.
     - Preserves missing IP addresses as `None` (never replaces with synthetic `0.0.0.0`).
     - Decouples boolean `notice` (in `weird.log`) from `notice_type` (in `notice.log`).
     - Captures and logs malformed lines in a structured `parse_error` table.
  4. **Multi-Process Concurrency:** Uses `concurrent.futures.ProcessPoolExecutor` with deterministic line slicing to bypass the Python GIL.
  5. **Genuine Benchmarking (`psutil`):** Measures genuine elapsed wall-clock time (`time.perf_counter()`), actual CPU usage percentage (`psutil.cpu_percent()`), and RSS memory consumption (`psutil.Process().memory_info().rss`). Verifies 100% dictionary equivalence between sequential and parallel parsed records.

---

### Engine 2 (E2): Rule-Based Threat Detection Engine
* **Location:** `E2_Threat_Detection/` (`e2_engine/`)
* **Core Role:** Evaluates normalized network events against 38 security rules and 7 supplementary heuristics using sliding-window anomaly detectors and max-heap prioritization.
* **Key Features:**
  1. **38 Zeek Transport & Network Rules:** Derived from `zeek_network_transport_alerts.xlsx`:
     - **R01–R05:** Port scans, address scans, packet fragmentation anomalies (`fragment_overlap`, `fragment_inconsistency`).
     - **R06–R14:** TCP handshake anomalies, SYN floods, Christmas Tree packets (FIN+PSH+URG flags active), FIN storms, `SYN_with_data`.
     - **R15–R27:** TCP sequence/window violations, connection originator SYN-ACK, window recision, bad checksums.
     - **R28–R38:** Tunnel encapsulation alerts (GRE, Teredo, AYIYA, IPv6-in-IPv4), DNS exfiltration indicators, capture loss thresholds.
  2. **Supplementary Heuristics:** Blacklisted IPv4/IPv6 detection, ICMP flood/sweep detection, and volume-based DoS anomalies.
  3. **Sliding-Window State Tracking:** Double-ended queues (`deque`) track event counts within sliding time windows (e.g. $\ge 15$ failed connections in 10s).
  4. **Alert Storm Cooldown:** Sliding interval suppression per `(rule_code, source_ip)`. Redundant triggers within the cooldown period increment `suppression_count` without emitting duplicate alerts.
  5. **Max-Heap Priority Queue:** Prioritizes outgoing alerts based on severity rank: `CRITICAL` (rank 1) $\to$ `HIGH` (rank 2) $\to$ `MEDIUM` (rank 3) $\to$ `LOW` (rank 4).

---

### Engine 3 (E3): Data Management & Persistence Engine
* **Location:** `E3_E4_Backend/backend/app/engines/e3_data_management/`
* **Core Role:** ACID-compliant storage of events, runs, alerts, audit metrics, and user credentials in a normalized 3NF relational schema.
* **Key Features:**
  1. **SQLite 3 in Third Normal Form (3NF):** 12 relational tables with foreign keys and strict `CHECK` constraints (e.g., ports $0 \le p \le 65535$, non-negative packet counts).
  2. **Write-Ahead Logging (WAL Mode):** Configures `PRAGMA journal_mode=WAL` and `PRAGMA busy_timeout=5000` to allow concurrent readers while batch transactions are being written.
  3. **Keyset Cursor Pagination:** Querying events uses cursor tuples `WHERE (event_timestamp, event_id) > (?, ?) ORDER BY event_timestamp ASC, event_id ASC LIMIT ?`. This avoids $O(N)$ query degradation caused by `OFFSET` on large datasets.
  4. **Error & Audit Trail:** Persists unparseable rows and validation rejections into a dedicated `parse_error` table referencing the specific `run_id` and line number.
  5. **Idempotent Alert Transactions:** Enforces `UNIQUE (run_id, rule_code, affected_ip, window_start)` to guarantee that re-evaluating a run never generates duplicate database alerts.

---

### Engine 4 (E4): REST API & Administrative Web Dashboard
* **Location:** `E3_E4_Backend/backend/app/engines/e4_api_dashboard/`
* **Core Role:** Exposes secure HTTP REST endpoints and renders an interactive, responsive graphical interface for system monitoring and alert triage.
* **Key Features:**
  1. **REST API (Flask 3.1):** Endpoints for authentication (`/api/v1/auth`), processing runs (`/api/v1/runs`), event queries (`/api/v1/events`), alert management (`/api/v1/alerts`), and benchmark metrics (`/api/v1/benchmarks`).
  2. **Role-Based Access Control (RBAC):** Token-based authentication using cryptographically secure session hashes. Restricts sensitive administrative operations (triggering runs, user creation) to `System Admin` while granting read/triage permissions to `Security Analyst` and `NetOps Admin`.
  3. **Interactive Frontend:** Single-page interface providing:
     - Real-time event counter cards and severity breakdown distributions.
     - Live Speedup & Throughput benchmarking graphs.
     - Event search with multi-field filters (Source IP, Port, Protocol, State).
     - Interactive Alert Triage (marking alerts as `OPEN`, `ACKNOWLEDGED`, or `RESOLVED`).

### Integration & Orchestration Layer
* **Location:** `Integration/Orchestration/coordinator.py`, `Integration/Contracts/`
* **Core Role:** Direct in-memory lifecycle coordinator that chains $E1 \to E3 \to E2 \to E3 \to E4$ without shell scripts or external message brokers.
* **Key Features:**
  - Manages atomic run status transitions: `RUNNING` $\to$ `COMPLETED` (or `FAILED` with logged traceback).
  - Guarantees error isolation: parsing errors in individual rows are recorded in `parse_error` while allowing valid rows to proceed to detection.
  - Enforces formal JSON schema contracts for event transfer and performance telemetry.

## 4. Key Algorithms & Mathematical Formulations

### Algorithm 1: Sliding-Window Threat Detection (E2)
* **Mechanics:** Events for each monitored source IP are pushed into a timestamp-ordered double-ended queue (`deque`). Prior to threshold checking, elements older than the window horizon ($t_{\text{current}} - W$) are evicted from the left of the deque in $O(1)$ amortized time.
* **Complexity:** Amortized $O(1)$ per event push/eviction; space complexity $O(K)$ where $K$ is the peak event density in window $W$.

### Algorithm 2: Max-Heap Priority Ordering (E2)
* **Mechanics:** Alerts are stored in a binary min-heap (`heapq`) ordered by:
  $$\text{Sort Key} = \left(\text{Priority Rank},\, -\text{Detected Timestamp},\, \text{Alert ID}\right)$$
  where `Priority Rank` is mapped as $\text{CRITICAL}=1, \text{HIGH}=2, \text{MEDIUM}=3, \text{LOW}=4$.
* **Complexity:** $O(\log M)$ insertion and $O(1)$ peak threat retrieval.

### Algorithm 3: Sliding Cooldown Alert Suppression (E2)
* **Mechanics:** Prevents alert floods during volumetric scans. When a rule triggers for an IP, its timestamp is stored in a suppression hash map. Repeat triggers within $T_{\text{cooldown}}$ seconds do not emit duplicate alerts; instead, they atomically increment the existing alert's `suppression_count`.

### Algorithm 4: Keyset Cursor Pagination (E3)
* **Mechanics:** Eliminates the $O(N)$ row-scan overhead of SQL `OFFSET` by seeking against the composite primary/unique key index:
  ```sql
  SELECT * FROM network_event 
  WHERE (event_timestamp, event_id) > (?, ?) 
  ORDER BY event_timestamp ASC, event_id ASC 
  LIMIT 100;
  ```
* **Complexity:** $O(\log N)$ B-Tree point seek regardless of whether the table contains 100 rows or 1,000,000 rows.

### Algorithm 5: Parallel Worker Chunking (E1)
* **Mechanics:** Slices $N$ log lines into $P$ balanced partitions of size $C = \lceil N/P \rceil$. Worker processes parse each partition in isolated memory spaces, attaching line ordinals so the coordinator reassembles events in deterministic sequence.

### Algorithm 6: Speedup & Telemetry Calculation
* **Speedup Ratio ($S$):** $S = T_{\text{sequential}} / T_{\text{parallel}}$
* **Throughput ($R$):** $R = \text{Total Records} / \text{Execution Time (seconds)}$
* **Telemetry:** Real CPU % and RSS physical memory in MB captured via `psutil`.

## 5. Database Architecture & Schema Specification (3NF)

The database `network_monitor.db` comprises 12 normalized tables adhering to **Third Normal Form (3NF)**:

1. **`role`**: RBAC roles (`System Admin`, `Security Analyst`, `NetOps Admin`).
2. **`user_account`**: User credentials with salted hashes and active status flags.
3. **`auth_session`**: Bearer token session tracking with timestamps and revocation checks.
4. **`protocol`**: Lookup table for network layer protocols (`tcp`, `udp`, `icmp`).
5. **`connection_state`**: Zeek connection states (`SF`, `S0`, `REJ`, `RSTO`, `OTH`, etc.).
6. **`severity_level`**: Urgency rankings (`CRITICAL`, `HIGH`, `MEDIUM`, `LOW`).
7. **`processing_run`**: Processing run metadata, input counts, valid counts, malformed counts, and execution status (`RUNNING`, `COMPLETED`, `FAILED`).
8. **`parse_error`**: Audit log of malformed rows with line numbers and error reasons.
9. **`network_event`**: Core table storing enriched connection records, microsecond timestamps, metrics (`total_bytes`, `bytes_per_packet`), and anomaly attributes.
10. **`performance_metric`**: Telemetry measurements per mode (`execution_time_sec`, `throughput_rec_sec`, `cpu_usage_pct`, `peak_memory_mb`).
11. **`benchmark_comparison`**: Speedup calculation and full-content equivalence status (`PASS`/`FAIL`).
12. **`alert`**: Generated threats with rule codes, affected IPs, detection timestamps, triage status (`OPEN`, `ACKNOWLEDGED`, `RESOLVED`), and suppression tallies.
13. **`alert_event_link`**: Many-to-many junction correlating alerts to contributing network events.

## 7. Viva & Review Defense Q&A

### Q1: Why did you eliminate the Java E1 implementation in Version 2?
> **Answer:** In Version 1, E1 had a standalone Java engine with Maven and 17 test classes, but the runtime coordinator and dashboard actually invoked the Python implementation to avoid JVM subprocess initialization latency. In Version 2, we eliminated this architectural debt by consolidating E1 into a pure Python multi-process engine (`ProcessPoolExecutor`). This removes all JVM/Maven installation prerequisites, avoids inter-process serialization overhead, and guarantees end-to-end maintainability with 100% native Python test coverage.

### Q2: How does your system guarantee that no alerts are lost if the database is locked?
> **Answer:** In `E2_Threat_Detection/e2_engine/e3_adapter.py`, we implement a transactional retry handler with backoff. If SQLite returns `SQLITE_BUSY` or reports that write transactions are temporarily queued, E2 does not discard the generated alerts. Instead, it retries flushing the batch up to 5 times. If the lock persists, E2 retains the alerts in its internal queue rather than dropping them.

### Q3: How do you handle Zeek logs with different separators or missing values?
> **Answer:** E1 dynamically reads Zeek header directives. It decodes `#separator \x09` (hex for tab) or `\x20` (space) and reads field order from `#fields`. For missing values (`-` or `(empty)` in Zeek), E1 explicitly maps them to Python `None` rather than fabricating synthetic timestamps or substituting `0.0.0.0` for missing IP addresses, preserving forensic accuracy.

### Q4: What is the benefit of Keyset Cursor Pagination over traditional LIMIT/OFFSET?
> **Answer:** With `OFFSET 10000`, the database engine must scan and discard 10,000 rows before returning the next batch, leading to $O(N)$ execution time that degrades severely on large tables. Keyset pagination queries the indexed primary key directly (`WHERE (event_timestamp, event_id) > (?, ?)`), enabling the B-Tree index to perform an $O(\log N)$ point seek regardless of dataset depth.

### Q5: How do you prevent alert storms when a host performs a port scan with thousands of packets?
> **Answer:** E2 uses a sliding cooldown suppression algorithm. When an alert fires for a given `(rule_code, affected_ip)`, an entry is made in a cooldown suppression dictionary with a timestamp. Any subsequent trigger for that same IP and rule within the cooldown window (e.g., 60 seconds) is suppressed, and only an internal `suppression_count` counter is incremented on the database record.
